1. Текстовий опис інженерних рішень
1.1 Детальний опис розгортання системи
1. Серверна частина: Розгорнута на базі фреймворку ASP.NET Core Web API. Для забезпечення зовнішнього доступу до локального сервера використано тунелювання через ngrok, що дозволяє IoT-пристрою (ESP32) звертатися до API за захищеним протоколом HTTPS.
2. База даних: Використано реляційну СУБД SQLite. Файл бази даних (Transport.db) розгорнуто локально разом із сервером. Взаємодія здійснюється через ORM Entity Framework Core, що забезпечує автоматичне створення таблиць на основі міграцій.
3. IoT Клієнт (ESP32 Emulation): Емуляція пристрою реалізована в середовищі Wokwi. Клієнт налаштований на підключення до віртуальної мережі Wi-Fi, синхронізацію часу через NTP-сервери та відправку HTTP POST запитів при спрацюванні датчика (натисканні кнопки). 
Для взаємодії IoT-клієнта із сервером використано тунелювання через ngrok. Оскільки сервер розгорнуто локально, симулятор у хмарі не має до нього прямого доступу. ngrok створює публічну HTTPS-адресу, яка перенаправляє всі запити від датчика безпосередньо на мій локальний порт. У налаштуваннях ESP32 ми вказали саме цю адресу як serverUrl, що забезпечує безперебійний зв'язок між залізом та бекендом через інтернет».
1.2 Обґрунтування вибору технологій
   * C# / ASP.NET Core: Вибрано за високу продуктивність, вбудовану підтримку Dependency Injection та зручну інтеграцію зі Swagger для тестування.
   * SQLite: Оптимальне рішення для IoT-проєктів завдяки відсутності потреби в окремому сервері БД та мобільності (база зберігається в одному файлі).
   * ESP32: Популярний мікроконтролер із вбудованим Wi-Fi стеком, що дозволяє реалізувати повноцінний HTTP-клієнт.
   * Swagger: Використано як графічний інтерфейс користувача та адміністратора для візуалізації роботи API без необхідності розробки окремого Frontend-додатка.

3. Фрагменти програмного коду
3.1 Логіка бізнес-процесів серверної частини (Розрахунок затримки)
Це основна частина коду в SensorController.cs, яка виконує математичну обробку:
[HttpPost("update")]
public async Task<IActionResult> UpdateLocation(int trainId, int stationId, string actualTime)
{
    var train = await _context.Trains.Include(t => t.Route).FirstOrDefaultAsync(t => t.Id == trainId);
    if (train == null) return NotFound("Поїзд не знайдено");


    var schedule = train.Route.FirstOrDefault(rs => rs.StationId == stationId);
    if (schedule != null)
    {
        train.CurrentStationId = stationId;
        // Математична обробка затримки
        if (TimeSpan.TryParse(actualTime, out var tActual) && 
            TimeSpan.TryParse(schedule.ScheduledArrival, out var tScheduled))
        {
            int delay = (int)(tActual - tScheduled).TotalMinutes;
            train.DelayMinutes = delay > 0 ? delay : 0;
        }
    }
    await _context.SaveChangesAsync();
    return Ok(new { status = "Дані отримано", delay = train.DelayMinutes });
}
3.2 Логіка адміністрування серверної частини
Для адміністрування використано стандартні CRUD операції, доступні через Swagger UI. Наприклад, отримання стану системи:
[HttpGet("trains")]
public async Task<ActionResult<IEnumerable<Train>>> GetTrains()
{
    return await _context.Trains.ToListAsync(); // Перегляд усіх поїздів адміністратором
}

void sendData() {
  String url = String(serverUrl) + "?trainId=1&stationId=2&actualTime=22:45";
  if (http.begin(client, url)) {
    http.addHeader("ngrok-skip-browser-warning", "69420"); // Обхід заглушки ngrok
    int httpCode = http.POST(""); 
    if (httpCode > 0) {
      Serial.println("Response: " + http.getString());
    }
    http.end();
  }
}
